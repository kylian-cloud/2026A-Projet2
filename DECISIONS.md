| Domaine | Notes de jeux vidéo Steam (« bon jeu ou non ») ; chances de battre un boss selon le loot ; vélos en libre-service ; réussite scolaire ; habitudes de vie et poids | **Basketball / NBA 2K.** Les jeux vidéo Steam ont été écartés parce qu'une autre équipe avait déjà ce sujet. L'idée du loot a été abandonnée : aucun jeu de données réel n'existe, et générer des données nous-mêmes aurait été refusé (le modèle n'aurait fait que retrouver notre formule). | Jeu de données | Steam Store Games (Kaggle) ; NBA 2K20 ou 2K25 seuls (environ 480 joueurs, moins de 500 lignes, sans stats réelles) ; assembler nous-mêmes notes 2K (HoopsHype) et stats (Basketball-Reference) | **CSV « stats NBA + note 2K »** trouvé sur GitHub : 2 412 lignes (un joueur pour une saison), saisons 2014-15 à 2019-20, 28 stats, aucune valeur manquante, aucun doublon joueur/saison. Il respecte tous les critères de taille et de type. Licence : aucune licence explicite, à signaler dans le README. | Oui (2026-11-13) |
| Ajout du poste des joueurs | Garder seulement `TEAM` comme variable catégorielle ; ajouter le poste | **Ajout de `POS`** (PG, SG, SF, PF, C) à partir de Basketball-Reference (tableaux de stats par match, 2014-15 à 2019-20), associé par nom de joueur et saison. C'est une variable catégorielle plus pertinente que l'équipe. 11 lignes ont été complétées à la main (Enes Kanter, Nicolas Claxton, Omer Asik : noms écrits différemment sur le site, tous pivots). Pour un joueur échangé en cours de saison, on garde le poste de sa première ligne. | Oui (2026-11-13) |
| Données personnelles | Garder les noms ; les retirer | **Retrait de la colonne `PLAYER`** des entrées du modèle, comme l'exige l'énoncé (aucune donnée identifiant une personne). | Oui (2026-11-13) |
| Sélection des variables | Version A : 8 variables (POS, AGE, GP, MIN, PTS, REB, AST, STL) ; version B : 11 variables (A + TEAM, BLK, FG%) ; les 28 stats | **10 variables : POS, AGE, GP, MIN, PTS, REB, AST, STL, BLK, FG%.** Colonnes retirées : `FP` (calculée à partir des autres stats), `W`/`L` (W + L = GP sur toutes les lignes), `OREB`/`DREB` (somme = REB), `FGM`/`FGA`/`3PM`/`3PA`/`FTM`/`FTA` (résumés par PTS et FG%), `DD2`/`TD3`/`PF`/`TOV`/`+/-` (peu parlants ou redondants). `TEAM` est retirée : 30 catégories pour un effet probablement nul. `BLK` est gardée pour les pivots, `FG%` pour l'efficacité au tir, que les points seuls ne mesurent pas. | — |
| Petits échantillons (peu de matchs) | Filtrer GP ≥ 10 (retire 134 lignes) ; filtrer GP ≥ 5 ; tout garder | **On garde toutes les lignes et on utilise GP comme variable.** Filtrer retirerait des stars blessées qui sont des cas réels (ex. Gordon Hayward 2017-18 : 1 match, note 88 ; Stephen Curry 2019-20 : 5 matchs, note 95). Avec GP comme variable, le modèle peut tenir compte de la fiabilité des stats. Limite assumée : il sous-estimera ces joueurs, ce qu'on montrera dans l'analyse des erreurs. | — |
| FG% = 0 sans aucun tir tenté (4 lignes) | Valeur sentinelle −1 ; `NaN` ; remplacer par la moyenne + colonne indicatrice ; supprimer les lignes | **Suppression des 4 lignes** (0,2 % des données). −1 aurait été lu comme un vrai nombre par le modèle, ce qui fausse le coefficient de FG% pour tous les joueurs. `NaN` est refusé par plusieurs modèles de scikit-learn. La colonne indicatrice ajouterait une variable et un champ dans l'interface pour seulement 4 lignes. | — |
| Répartition du travail | Découpage par module ; découpage par couche, chacun une partie de l'interface | **A (Kylian) : données + saisie** (donnees.py, exceptions.py, graphique d'exploration, champs et validation de l'interface, test_donnees.py, README). **B (Aziz) : modèle + résultats** (modele.py, historique.py, main.py, prédiction, graphique et historique de l'interface, test_modele.py, JOURNAL_IA.md). Chacun écrit du code dans l'interface, et chacun doit pouvoir expliquer tout le projet. | — |
| Ce que retourne le nettoyage | DataFrame propre seul ; tuple (X, y) ; DataFrame emballé dans un objet `JeuDeDonnees` | **`nettoyer()` retourne un DataFrame, emballé ensuite dans `JeuDeDonnees`** (qui donne `entrees()`, `cible()`, `variables`). La fonction reste simple et testable seule. La classe évite de recalculer min/max et catégories dans `modele.py` et réalise la composition (JeuDeDonnees contient des Variable). | — |
| Format des métadonnées | Dictionnaire par colonne ; listes séparées (colonnes, catégories, intervalles) ; liste de variables | **Liste `variables`** où chaque élément est le `vers_dict()` d'une Variable (`nom`, `type`, `etiquette`, `min`/`max` ou `valeurs`), plus `cible`, `modele` et `metrique`. Elle garde l'ordre des champs, et l'interface recrée les objets avec `variable_depuis_dict()`. | — |
| Cible et métrique | Note 2K ; catégories de note | **`rankings` et RMSE.** La RMSE s'exprime en points de note et permet de comparer le modèle à la référence sur le même ensemble de test. | À valider (validation C) |
| Modèle et référence | Forêt aléatoire ; prédiction constante | **`RandomForestRegressor` avec `POS` encodé par `OneHotEncoder` dans un pipeline.** Comparaison avec `DummyRegressor(strategy="mean")`, graine 42 et 300 arbres. | À valider (validation C) |
| Technologie d'interface | Tkinter ; Streamlit ; Gradio ; PyQt/PySide | **Streamlit.** Moins de code de mise en page, ce qui laisse plus de temps pour le modèle et les tests. Composants prêts (`selectbox`, `dataframe`, `pyplot`) et rendu moderne. La POO du projet est dans `donnees.py` et `modele.py` (héritage Variable, composition JeuDeDonnees/Application) : elle ne dépend pas de la technologie d'interface. Inconvénient assumé : le script se ré-exécute à chaque clic, d'où `st.cache_resource` et `st.session_state`. Tkinter a été écarté (plus long à coder), PyQt aussi (trop lourd pour 6 jours). | À valider (validation D) |
| Cible et type de problème | Classification (ex. « star » si note ≥ 85) ; régression | **Régression sur `rankings`** (note 2K de 62 à 98). Prédire le nombre exact est plus informatif pour l'utilisateur qu'une catégorie, et découper la note en classes aurait été arbitraire. | À valider (validation C) |
| Métrique | RMSE ; MAE ; R² | **RMSE.** Elle s'exprime dans l'unité de la note (« on se trompe d'environ X points sur 99 »), donc elle est facile à expliquer. Elle pénalise davantage les grosses erreurs, ce qui fait ressortir les stars blessées que le modèle sous-estime. La MAE cache ces grosses erreurs, et le R² est moins parlant pour un non-informaticien. Elle est calculée avec NumPy et comparée à scikit-learn dans un test. | À valider (validation C) |
| Modèle | Régression linéaire ; arbre de décision ; forêt aléatoire ; k plus proches voisins | **Forêt aléatoire** (`RandomForestRegressor`, `random_state=42`), comparée à une référence qui prédit toujours la moyenne (`DummyRegressor`). Elle capte les effets non linéaires (l'effet de GP n'est pas proportionnel) et fournit l'importance des variables, utilisée pour le graphique de l'interface. Un arbre seul sur-apprend facilement : il apprend les joueurs d'entraînement « par cœur ». Les k-NN demandent de normaliser et sont moins bons ici. Une régression linéaire pourra être ajoutée comme second modèle de comparaison si le temps le permet. Sur-apprentissage à surveiller : comparer la RMSE sur l'entraînement et sur le test. | À valider (validation C) |
